Make agent failures inspectable

When an agent gives a wrong answer, the final response rarely explains whether the problem came from the model, a tool, or a delegated task. OrcView combines a Python agent runtime with a live dashboard so developers can inspect those steps, their costs, and the condition that stopped the run.

An explicit runtime, from execution to replay

The runtime uses four states: Start → Reasoning ⇄ Acting → Done. Reasoning requests the next model response; Acting executes requested tools and returns their results to the model. State transitions are emitted by the execution loop itself, so the dashboard follows the control flow that actually ran.

A child agent implements the same callable interface as a tool. Its events carry a sub-run identifier through the parent’s event stream, while the parent model receives the child’s answer rather than its internal trace. This keeps delegation and ordinary tool use on one execution path and lets the dashboard drill into child runs through one server-sent event connection.

Each run captures the model, prompt, enabled tools, and execution limits at startup. The recorder collects and forwards events in memory. Local SDK operators can explicitly enable SQLite recording with record_runs=True; it is disabled by default. The public dashboard isolates temporary configuration/history per browser session instead of sharing a database.

Opening a recorded child run filters events already loaded in the browser and feeds them through the same event renderer. This avoids another model call or server request for the drill-down.

The ancestor set is copied when delegation extends the chain, rather than shared as a mutable list. Independent branches therefore cannot overwrite each other’s ancestry. Retry and validation policies remain explicit application choices instead of silently changing every agent’s behavior.

Five controlled failures

The saved deterministic fault suite passed 5/5 injected scenarios using fake model responses. These checks isolate enforcement and event recording; they do not measure production reliability or model accuracy.

Injected scenarioObserved behavior
Malformed structured outputOne validation failure recorded; invalid output rejected
TimeoutFirst attempt failed; traced retry succeeded on attempt two
HTTP 429First attempt failed; traced retry succeeded on attempt two
A → B → A delegation cycleOne cycle error traced; parent continued and returned “cycle handled”
Two tool requests with a one-call limitOnly the first tool executed; guardrail and stop error recorded

In the cycle case, A delegates to B, and B requests A. The ancestor check rejects that request before another model call. B emits the error and closes its run; A receives the child result and produces its final response. The saved event sequence connects the originating tool call, nested failure, and parent continuation instead of reducing the whole interaction to a single error message.

The accompanying microbenchmark measured 115.3 ns of incremental recording overhead per event over a direct callback, using nine repeats of 250,000 events. This isolates appending and forwarding an event in-process; database writes, dashboard rendering, network traffic, and model latency are excluded.

A trace exposed a scoring defect

One beyond-tool result expected Eva, but the agent concluded Bob. The saved grader still marked it correct because “Eva” appeared elsewhere in the answer table. The raw artifact remains available, but the aggregate must be regenerated with a stricter final-answer extractor before it is reported as a result.

Complete answers and tool traces are retained so aggregate scoring can be audited.

Evaluation limits

  • The saved evaluations use one synthetic 200-row sales dataset and do not establish general data-analysis accuracy.
  • Model-judge agreement is secondary to deterministic value checks and can share model biases.
  • Latency and cost are properties of one saved run and model configuration, not service-level guarantees.
  • The beyond-tool tests show that recording agent behavior can expose failures; it does not itself prevent fabricated answers.
